# ADR-0009: 프로젝트 카탈로그 포지셔닝 — 보조 기능으로 의도적으로 얕게 유지

- **상태**: 확정
- **날짜**: 2026-08-12
- **근거 문서**: BENCHMARK.md 3.6·4·5.9, claude-do.md, PRD.md §1.1, README.md

## 배경

경쟁 벤치마킹 재검토(BENCHMARK.md 3.6, 2026-08-11 추가)가 지적한 것: Phase 2에서 실제로 구현된 기능(Project Entity 등록/검색 — ADR-0004, 기술 스택 태깅 — ADR-0005, 유사 프로젝트 탐색 — ADR-0006)은 코드 관계 분석기가 아니라 Backstage류 "서비스 카탈로그 / 내부 개발자 포털" 제품군과 기능적으로 겹친다. 그런데 README.md·PRD.md의 제품 소개 문구는 여전히 "코드 관계 분석기"만을 전제로 쓰여 있어, 실제 구현 범위와 대외 포지셔닝이 어긋나 있었다(BENCHMARK.md 5.9).

더 근본적인 질문은 문구 정합성이 아니라 **방향 결정 자체가 로드맵 어디에도 없었다**는 것이다 — 카탈로그 기능을 Backstage와 정면 경쟁할 만큼 키울지, 아니면 코드 관계 그래프의 보조 기능으로 의도적으로 얕게 유지할지.

## 결정

**카탈로그 기능은 코드 관계 그래프의 보조 기능으로 의도적으로 얕게 유지한다. Backstage와 정면 경쟁하지 않는다.**

BENCHMARK.md §4가 이미 정확한 표현을 찾아냈다 — 이 ADR은 그 표현을 공식 결정으로 승격한다:

> ContextSource는 "카탈로그 제품에 코드 그래프를 얹은 것"이 아니라 "코드 관계 그래프에 최소한의 카탈로그 레이어가 자연스럽게 얹힌 것"에 가깝다.

이유:

1. **claude-do.md의 명시적 금지사항과 직결된다.** "다중 Project 지식 그래프 확장"과 "Vector Search 추가"는 최초 구현 지시서가 금지한다(claude-do.md). Backstage와 정면 경쟁하려면 소유권(owner) 모델, 플러그인 생태계, 조직 단위 거버넌스 같은 카탈로그 자체의 깊이가 필요한데, 이는 이 프로젝트의 핵심 정체성(BENCHMARK.md §7: "Evidence 기반 TypeScript 변경 영향 탐색기")에서 멀어지는 방향이다.
2. **이미 그렇게 설계되어 있다.** ADR-0006이 유사 프로젝트 탐색을 순수 기술 스택 태그 교집합으로 설계하고 Vector Search·영속적 Project 간 그래프 관계를 명시적으로 배제한 것, Project 등록이 `catalog-info.yaml` 같은 별도 메타데이터 파일이 아니라 기존 코드 분석 파이프라인이 이미 읽는 `tsconfigPath`/`package.json`을 그대로 재사용하는 것 모두 "보조 기능" 방향과 일치한다 — 이 ADR은 새 제약을 추가하는 게 아니라 이미 내려진 개별 결정들의 공통 방향을 명문화한다.
3. **0일차 프로젝트가 두 카테고리를 동시에 개척할 여력이 없다.** Backstage는 CNCF 소속 오픈소스로 수년간 수천 개 기업이 검증한 카탈로그 제품이다(BENCHMARK.md 3.6). 단일 작성자 프로젝트가 카탈로그 깊이에서 그와 경쟁하는 것은 "이들에게서 무엇을 배워 차별화할 것인가"(BENCHMARK.md §7의 0일차 프로젝트 전제)라는 이 프로젝트의 벤치마킹 목적과 맞지 않는다.

**차별점은 명시하되, 범위는 넓히지 않는다**: Backstage 대비 실제로 존재하는 차별점 — 수동 YAML 등록이 아니라 `package.json` 자동 감지(ADR-0005)로 시작한다는 점, 카탈로그 메타데이터가 코드 관계 그래프와 같은 저장소·같은 조회 계층을 공유한다는 점(Shared Context 원칙) — 은 문서 포지셔닝에 명시한다(→ README.md/PRD.md 갱신, 이 ADR의 실행 항목). 그러나 이 명시는 카탈로그 기능을 더 만들라는 신호가 아니다.

## 하지 않는 것

- 소유권(owner)/팀 모델, `catalog-info.yaml` 같은 별도 카탈로그 메타데이터 포맷, 플러그인 생태계 등 Backstage가 가진 카탈로그 고유 기능을 추가하지 않는다.
- 카탈로그를 위한 새 Entity 종류나 Project 간 영속적 관계를 추가하지 않는다(claude-do.md 금지사항, ADR-0006과 일관).
- README.md/PRD.md를 "카탈로그 제품"으로 다시 쓰지 않는다 — 한두 문장으로 존재를 인정하고 차별점을 밝히는 선에서 그친다.

## 재검토 조건

실제 사용자가 카탈로그 기능(소유권, 팀 단위 검색, 외부 시스템 연동 등)을 반복적으로 요청하는 시점에 재검토한다. 그 전까지는 코드 관계 그래프가 1급 기능이고 카탈로그는 그 조회 계층을 공유하는 보조 기능이라는 위계를 유지한다.
