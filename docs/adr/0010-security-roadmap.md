# ADR-0010: 보안 로드맵 — 로컬 단일 사용자 전제의 유효기간과 최소 API Key 보호장치

- **상태**: 확정
- **날짜**: 2026-08-12
- **근거 문서**: PRD.md NFR-6, BENCHMARK.md 5.12, IMPLEMENTATION_REPORT.md §10·§11-5

## 배경

HTTP API와 MCP 서버 모두 인증이 전혀 없다(IMPLEMENTATION_REPORT.md §10). PRD NFR-6("로컬 또는 사용자 통제 환경")이 이를 정당화했지만, Phase 2에서 "여러 프로젝트를 하나의 서버가 관리"하는 형태로 이미 진화했고, Docker Compose는 포트를 호스트에 바인딩해 네트워크로 노출한다(README.md 실행 방법). `DELETE /projects/{id}`는 CASCADE로 관련 데이터를 전부 지우는데 이를 막을 권한 체계가 없다(BENCHMARK.md 5.12).

두 가지가 결정되지 않은 채 남아 있었다: (1) "로컬 단일 사용자 전제가 언제까지 유효한가"라는 로드맵 질문, (2) 그 전제가 유효한 동안에도 최소한의 보호장치를 넣을지.

## 결정 1 — 로컬 단일 사용자 전제는 "원격/다중 사용자 배포가 실제로 요청되기 전까지" 유효하다

이 프로젝트는 PRD NFR-6에 따라 로컬 또는 사용자가 직접 통제하는 환경에서의 단일 사용자 실행을 전제로 설계되어 있다 — Project 등록이 서버 프로세스가 읽을 수 있는 로컬 파일시스템 경로(`workspace-root` 기준 상대 경로)를 요구하는 것부터 이 전제에 의존한다. 이 전제를 다중 사용자 인증·인가 모델(사용자 계정, 역할, Project별 접근 제어)로 바꾸는 것은 별도의 설계가 필요한 큰 변경이며, claude-do.md가 정의한 현재 범위 밖이다.

**그러므로**: 실제 사용자가 "여러 사람이 원격으로 같은 서버를 공유해야 한다"를 요청하기 전까지는 이 전제를 유지한다. Docker Compose로 포트를 호스트에 바인딩해 네트워크로 노출하는 것은 "로컬 단일 사용자가 자신이 통제하는 환경에서 원격 접근한다"는 시나리오까지는 NFR-6 범위 안이라고 본다 — 다만 그 경우에도 실수로 파괴적 오퍼레이션이 실행되는 것을 막을 최소 장치는 필요하다(결정 2).

## 결정 2 — 파괴적/변경 오퍼레이션에 옵트인 API Key 보호장치를 추가한다

IMPLEMENTATION_REPORT.md §11-5가 이미 권고했던 "로컬 외 환경 배포 시 최소한의 인증(API key 등)"을 구현한다. 범위는 최소로 유지한다:

- **모든 비-`GET`/`HEAD`/`OPTIONS` 요청**(`POST`/`PATCH`/`DELETE` — 프로젝트 등록·수정·삭제, 기술 스택 변경, 분석 실행 등)에 `x-api-key` 헤더 일치를 요구한다. `GET` 조회는 계속 완전히 열려 있다 — Web UI가 매 조회마다 키를 주입해야 하는 마찰을 만들지 않기 위함이고, 이 프로젝트의 위협 모델에서 진짜 위험은 "조회당함"이 아니라 "삭제·변조당함"이기 때문이다.
- **완전히 옵트인이다.** `AppContext.apiKey`(→ CLI `--api-key` / 환경변수 `CONTEXTSOURCE_API_KEY`)를 설정하지 않으면 기존 동작과 100% 동일하다 — 기본값은 여전히 "로컬 단일 사용자, 인증 없음"이다. 기존 로컬 개발 워크플로(README.md `make run-api`, Web UI dev server)를 깨지 않는다.
- **역할 기반 접근 제어나 사용자 계정을 도입하지 않는다** — 단일 공유 비밀(shared secret) 하나로 "이 키를 아는 사람만 변경할 수 있다"만 보장한다. 여러 사용자를 구분하거나 Project별로 다른 권한을 주는 것은 다루지 않는다.
- Docker healthcheck가 쓰는 `GET /health`는 API key 미들웨어 적용 대상 밖에 둔다(라우터가 아니라 app에 직접 등록되어 있어 자연스럽게 영향을 받지 않는다) — 컨테이너 생존 확인은 키 없이 항상 동작해야 한다.

이유:

1. **위협 모델에 비례하는 최소 조치.** 지금 실제로 존재하는 위험은 "네트워크에 노출된 포트로 아무나 `DELETE /projects/{id}`를 호출해 데이터를 지울 수 있다"는 것이지, "아무나 조회할 수 있다"가 아니다(애초에 소스 코드 자체가 로컬에 있고, Query 결과도 그 소스 코드에서 파생된 값이라 조회 노출의 한계 위험이 삭제 위험보다 낮다). 최소 조치로 실제 위험만 막는다.
2. **claude-do.md/PRD 범위를 넘는 인증 시스템을 만들지 않는다.** JWT, 세션, 사용자 DB 같은 본격적인 인증 계층은 이 프로젝트의 "로컬 단일 사용자" 정체성과 맞지 않고, 지금 요청되지 않은 기능이다(YAGNI).
3. **하위 호환이 전제조건이다.** 이미 이 프로젝트를 로컬에서 쓰고 있는 사용(자기 자신 포함)이 옵션 하나 켜지 않았다고 깨지면 안 된다.

## 하지 않는 것

- **Web UI에 API key를 심지 않는다.** 브라우저에 배포되는 정적 JS 번들에 넣는 값은 페이지에 접근할 수 있는 누구에게나 보이므로 진짜 비밀이 아니다 — 여기서 키를 심는 건 진짜 보호가 아니라 보호하는 척(security theater)이다. 그러므로 API key를 켜면 **Web UI의 변경 오퍼레이션(프로젝트 등록/삭제, 기술 스택 편집, 분석 실행)도 401로 막힌다** — 이는 버그가 아니라 의도된 동작이다. 이 옵션의 위협 모델은 "API 포트에 직접 요청을 보낼 수 있는 임의의 네트워크 클라이언트를 막는다"이지 "Web UI만 예외적으로 신뢰한다"가 아니다. Web UI의 쓰기 기능이 필요하면서 API key도 켜고 싶다면, 키를 아는 사람만 Web UI 자체에 접근하게 하거나(예: 별도 리버스 프록시 인증), 로컬/신뢰된 환경에서만 Web UI를 띄우는 것이 맞는 사용 방식이다.
- 사용자 계정/세션/역할 기반 접근 제어(RBAC)를 도입하지 않는다.
- MCP 서버에 인증을 추가하지 않는다 — MCP는 stdio transport로 로컬 프로세스 간 통신이며 네트워크에 노출되지 않는다(API.md §3). 이 ADR의 위협 모델(네트워크 노출) 밖이다.
- API key를 기본값으로 강제하지 않는다 — 옵트인을 유지한다.
- 키 회전(rotation), 다중 키, 만료 등 키 관리 기능을 만들지 않는다 — 환경변수 하나로 값을 바꾸고 서버를 재시작하면 된다.

## 재검토 조건

여러 사용자가 실제로 하나의 배포된 서버를 공유해야 하는 요구가 생기면(예: 팀 단위 배포), 이 ADR의 "단일 공유 비밀" 모델을 사용자 계정 기반 인증으로 교체하는 것을 별도 ADR로 재검토한다.
